Several drafts contain the same move—cheap cognition makes context, memory and coordination more important—under different metaphors. The next pass should make the differences more useful, rather than making every essay more comprehensive.

This review covers all 11 draft projects: 10 active projects and the published Almanac package. The original **How Durable Is the Target?** treatment was preserved. A later privacy pass removed identifiable client examples from the imported Almanac and its research review copy at the writer’s request. For a more immediate AI strategy sequence, finish **Every Handoff Is a Claim** and **What Survives the Match?** after a worked example for each. Their frameworks could become useful workshop instruments. The diagrams alone do not establish that they improve decisions.

## Core repo recommendations, in priority order

These are proposed changes; this editorial branch does not alter the renderer, importer, validation logic or Actions workflows.

### 1. Make the editorial handoff a first-class part of a draft

Keep the existing four-file package. Give each README a short current contract: **reader, distinct claim, unresolved objection, next move**. Put decisions and rejected directions in `notes.md`; put evidence status in `sources.md`. Avoid requiring elaborate metadata when capturing a thought.

Then render the next move and blocker on the drafts index. “Drafting” currently describes all 10 active projects and does little to help choose work. A view that says “needs one scene,” “needs one experiment,” or “author pass” would be more useful than another chronological file list.

**Small first change:** agree the four fields in prose, use them for two sessions, then decide which deserve frontmatter and validation. The handoffs in this pass are a starting point, not a new schema.

### 2. Preserve editorial decisions and author voice outside chat

AGENTS.md already protects captures and published work and supports named treatments. It does not contain the specific instruction to preserve the original `automating-the-wrong-layer/draft.md`; that was recovered from the conversation. Put treatment-specific restrictions beside the treatment, where every client can discover them.

Add one concise editorial guide with links to actual voice exemplars. The current corpus contains useful contrasts: [Taking Blogging Seriously](published/2025-06-27-taking-blogging-seriously.md) for lived detail and emotional purpose; [Termites & Tokens](published/2026-06-08-of-termites-tokens.md) for a strange metaphor that generates questions; [Google is Grounded](published/2025-03-21-google-is-grounded-and-needs-to-learn-how-to-soar.md) for an argument supported by a working intervention.

Suggested principles: preserve odd details and useful doubt; identify the mechanism; keep a metaphor only while it reveals something; do not invent first-person scenes; resist adding an academic source merely to dignify an observation. Avoid giving every draft the same sequence of short declarations and “the real question is” pivots.

**Small first change:** a one-page guide plus a decision note when an alternative is rejected. Do not build a wiki of every sentence choice.

### 3. Turn bibliographies into evidence for claims

The `sources.md` files are valuable but mix verified findings, remembered summaries, research leads and unavailable local paths. A long list of links can look like a fact check without being one.

For the few load-bearing claims in each essay, record: claim, source, page or section, what was actually checked, date, and limitation. Keep unused sources below under research leads. Distinguish empirical findings, theoretical results, analogies, predictions and hypothetical examples.

The memory rewrite demonstrates the payoff: [MemGPT](https://arxiv.org/abs/2310.08560) is an existing counterexample to “AI has only two memory layers.” Recognizing it made the argument more interesting—maintenance and revision became the actual problem.

**Small first change:** claim-level checks for the next piece to publish, not a mandatory database migration for every old note.

### 4. Backfill the relevant published archive deliberately

There are **11 published files, six captures and no populated seeds** in this checkout. `plot.yml` configures only the main blog’s feed. The importer processes what the feed exposes; it is not an archive crawler. It skips known URLs/GUIDs, so an earlier excerpt import will not later be upgraded automatically.

The consulting essay references many older pieces not available in the local corpus. That weakens the instruction to learn voice and avoid repetition from `published/`.

**Small first change:** a curated URL manifest for the consulting chapters and NEW MBA essays actually cited by active drafts. Import full text with provenance, report extraction completeness, and review replacements explicitly. Do not assume repeatedly fetching RSS fills historical gaps.

No need to manufacture seeds because the directory is empty. The essays have recurring concepts worth mapping, but a seed should become useful working material before it becomes a lifecycle obligation.

### 5. Fix the import-to-Pages handoff and concurrent bot writes

In [import-published.yml](.github/workflows/import-published.yml), the importer commits with `GITHUB_TOKEN` and rebuilds indexes. Its own comment correctly notes that those pushes do not trigger other workflows. [pages.yml](.github/workflows/pages.yml) listens only to qualifying pushes and manual dispatch. Consequently, an imported post can remain absent from the site until another qualifying push or manual deployment.

The importer and [index rebuild](.github/workflows/indexes.yml) also independently check out, commit and push to main without a shared serialization mechanism or retry after a non-fast-forward rejection. This is a race risk identified from the workflow definitions, not a claim that a particular run failed.

**Small first change:** deploy after a successful import using a deliberate workflow handoff or shared job; serialize canonical bot writes and regenerate from a fresh checkout when retrying. Test the “new import, no human push” path. Longer term, decide whether committing derived indexes is worth the extra branch churn, since the site already builds directly from Markdown.

### 6. Add narrow validation and remove stale template instructions

The validator checks capture metadata and declared manuscript existence, but does not validate draft status values, draft dates or the `published_manuscript` reference. It can accept a published project pointing at a nonexistent selected treatment. Internal-link validation is regex-based and does not verify anchor targets or external-source correctness.

Add only meaningful gates: valid draft dates/statuses, an existing selected published manuscript, and valid declared manuscript paths. Keep uncertain editorial judgments out of CI. A successful build cannot prove an essay’s claims.

The root README still tells new users to delete `captures/2026/08/*` as “three example captures.” This is now Tom’s real capture directory with six entries. It also references example seed/draft/published files that no longer exist. Move template onboarding into separate documentation and make the root README describe this working repository.

**Small first change:** remove the stale deletion recipe and test the published-treatment reference. Save a larger site refactor for a concrete need.

## A workflow that would make this useful

A returning session should begin with one editorial choice: which next move can we complete now? “Make all the drafts better” is useful occasionally; it should not be the default recurring action.

1. Choose one piece and read its checkpoint, manuscript and source limitations.
2. Identify the smallest intervention that changes the argument: a scene, counterexample, source check, worked case or cut.
3. Do that work. A research session may end with an objection rather than more prose.
4. Update the checkpoint with what changed, what was rejected and what would change the decision.
5. Make one reviewable commit. Before publication, read the essay without the notes and check its load-bearing claims.

For a twenty-minute session, ask: **“What would make this draft more true or more mine?”** Then choose one answer. The system should lower the effort of returning to a thought, not create a second writing job managing the system.
